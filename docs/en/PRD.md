## 1. Project Overview

### 1.1 One-Sentence Positioning
A locally running functional-level simulator for the ESP32 family of MCUs, offering "virtual breadboard"-style graphical peripheral assembly, real firmware flashing, and GDB debugging, positioned for teaching, prototype validation, and CI automated testing.

### 1.2 Target Users
- Embedded learners (can validate code without hardware).
- Firmware developers (fast regression testing, peripheral timing-logic validation).
- Teaching and training organizations.

### 1.3 Non-Goals (explicitly excluded)
This project does **not** pursue:
- Electrical-level / SPICE-level circuit simulation (no modeling of resistors, capacitors, current, or parasitic parameters).
- Nanosecond-level timing accuracy (no real-time guarantee; a logical clock is used).
- True RF simulation of WiFi/BLE wireless protocols (the MVP only provides API placeholders returning mocks).
- Coverage of non-ESP32 chips (the MVP covers only the classic ESP32; S3/C3 come later).

### 1.4 Success Criteria (MVP acceptance)
1. Can load an Arduino-compiled `blink.elf`, start the simulation, and see the LED peripheral turn on and off on the UI following the GPIO level.
2. Can set breakpoints, step, and inspect global variables and registers via GDB.
3. Can drag an LED, a push button, and an SSD1306 OLED onto the virtual breadboard and wire them to GPIO.
4. Graphics drawn by the firmware render correctly on the OLED (frame-identical).
5. Provides a UART serial console where `printf`/`Serial.print` output is visible.
6. The whole flow completes locally (desktop app) with no network dependency.

## 2. Terms and Glossary

| Term | Meaning |
|---|---|
| Simulation core / Sim Core | The part responsible for executing ESP32 instructions and modeling the peripheral buses (based on QEMU-ESP32) |
| Bridge (桥) | A Node.js process that manages the QEMU subprocess, GDB, peripheral models, and IPC with the UI |
| Peripheral model / Peripheral Model | The behavioral implementation of an external part (LED/OLED/buzzer, etc.), running on the Bridge side |
| Netlist (网表) | Structured data describing GPIO↔peripheral pin connections |
| Logical clock / Logical Clock | Discrete time steps by which the simulation advances, not real wall-clock time |
| DBus channel / DBus Channel | A socket channel through which the QEMU custom device forwards bus transactions to the Bridge |
| Project (工程) | A `.breadesp` project directory containing firmware, netlist, and peripheral configuration |
| DAP | Debug Adapter Protocol (VS Code debugging protocol, optional backend) |

## 3. Functional Requirements

### 3.1 Firmware Loading and Flashing (F-FW)
- F-FW-1 MUST support loading ELF firmware (with symbols, required for debugging).
- F-FW-2 SHOULD support loading a bare `.bin` (run only, no variable debugging).
- F-FW-3 MUST support selecting the target chip model (MVP: `ESP32`).
- F-FW-4 MUST display the memory map, entry address, and symbol table summary after loading.
- F-FW-5 MAY validate at load time that the ELF architecture matches the chip model, warning on mismatch.

### 3.2 Simulation Control (F-SIM)
- F-SIM-1 MUST provide: start, pause, reset, stepping (instruction level), quit.
- F-SIM-2 SHOULD provide a simulation speed multiplier (0.1x–10x, logical clock throttling).
- F-SIM-3 MUST allow GDB interaction while paused.
- F-SIM-4 MUST broadcast simulation state changes to the UI in real time (running/paused/stopped/error).

### 3.3 Debugging (F-DBG)
- F-DBG-1 MUST support: breakpoints (function/address/line number), deleting breakpoints, clearing breakpoints.
- F-DBG-2 MUST support: step into, step over, continue.
- F-DBG-3 MUST support: viewing/modifying registers, viewing/modifying memory, viewing global/local variables.
- F-DBG-4 SHOULD support: conditional breakpoints, watchpoints.
- F-DBG-5 MUST communicate with `xtensa-esp32-elf-gdb` via GDB/MI; on the UI side this is wrapped as a unified `Debugger` interface.
- F-DBG-6 SHOULD expose a DAP adapter for easy integration with VS Code.

### 3.4 Virtual Breadboard (F-BB)
- F-BB-1 MUST provide a canvas on which peripheral parts, breadboard wires, and power/ground markers can be placed (logical only, no electrical semantics).
- F-BB-2 MUST support drag-and-drop placement from the part palette: LED, push button, SSD1306 OLED (MVP set).
- F-BB-3 SHOULD extend to: ST7789 TFT, buzzer, speaker (I2S), microphone (I2S/ADC), rotary knob, servo.
- F-BB-4 MUST persist wiring as a "netlist", separate from the UI layout (layout is visual only; the netlist is logic).
- F-BB-5 MUST support undo/redo (at least 20 steps).
- F-BB-6 MUST support saving/loading a project (`.breadesp` directory).
- F-BB-7 SHOULD provide a switchable 3D modeling view: orbit rotation/zoom/pan, part dragging with grid snapping, pin wiring, and real-time state presentation; it shares the same netlist and layout with the 2D canvas, and the project file introduces no 3D coordinates.

### 3.5 Peripheral Interaction (F-PER)
- F-PER-1 LED: turns on and off in real time according to the level of the connected GPIO; supports PWM brightness (duty cycle → brightness).
- F-PER-2 Push button: clicking in the UI toggles the level, generating edge events injected into the GPIO input.
- F-PER-3 OLED (SSD1306, I2C 0x3C): intercepts I2C commands, maintains a 128×64 framebuffer, and pushes each frame to the UI Canvas.
- F-PER-4 TFT (ST7789, SPI): intercepts SPI commands, maintains a framebuffer, and renders.
- F-PER-5 Buzzer: listens to the GPIO/PWM frequency and synthesizes a square wave through WebAudio.
- F-PER-6 Speaker (I2S): intercepts the I2S DMA PCM stream and plays it at the sample rate.
- F-PER-7 Microphone: user-uploaded/generated waveforms or local microphone capture, injected into the I2S/ADC input buffer at the sample rate.
- F-PER-8 Oscilloscope (bonus): captures GPIO/PWM/I2S data streams and draws timing diagrams.

### 3.6 Serial Port (F-SER)
- F-SER-1 MUST display UART0 output with ANSI color support.
- F-SER-2 SHOULD support injecting input into UART0 (send on Enter).

### 3.7 Project (F-PROJ)
- F-PROJ-1 MUST have the project structure: `firmware.elf`, `netlist.json`, `layout.json`, `meta.json`.
- F-PROJ-2 MUST support new/open/save as.
- F-PROJ-3 MAY support linking to a PlatformIO/IDF project directory (auto-discovering `build/*.elf`). The link is recorded in `meta.json` as `external: {kind, dir}` (`kind` ∈ `platformio`|`esp-idf`; the field is optional and backward compatible when absent); identification rules: PlatformIO is identified by `platformio.ini` (`[env:x]` sections map to `.pio/build/<env>/*.elf`; a bare `[env]` maps to the `env` directory; the union of declared envs and on-disk env directories is taken), ESP-IDF is identified by `CMakeLists.txt` plus (`sdkconfig` or a `project.cmake` include) (scanning the top level of `build/*.elf`); candidates are sorted by mtime newest → oldest; import copies through the F-FW-5 architecture gate into the in-project `firmware.elf`, and an explicit path must be one of the current scan candidates.

### 3.8 Extensibility (F-EXT)
- F-EXT-1 MUST provide a peripheral SDK allowing third parties to register peripheral models as independent packages.
- F-EXT-2 MUST keep the peripheral model interface stable (see §6.2).
- F-EXT-3 SHOULD provide a peripheral marketplace placeholder (local directory scan; no online marketplace in the MVP). P5.2 delivery contract:
  - Local directory: defaults to `<user home>/.breadesp/peripherals/` (overridable via `BREADESP_PERIPHERALS_DIR`); each **subdirectory** is one peripheral package.
  - Package format: the directory contains a `breadesp-peripheral.json` manifest and an entry JS module. Manifest fields: `manifestVersion: 1`,
    `name` (lowercase kebab, may carry `@scope/`), `version` (the package's own semver), `displayName`, `entry` (relative path,
    which must resolve inside the package directory), optional `description` / `sdkVersion` (major gating per §6.2 pre-checked at scan time; marked
    `incompatible` if higher than the host) / `provides` (declared kind list, presentation only; actual kinds are determined by the registration diff).
  - Entry contract: the module SHOULD default-export `(host: PeripheralHostApi) => void | Promise<void>`; `host` carries the
    host's own `registerPeripheral` and `PERIPHERAL_SDK_VERSION` (avoiding dual-instance resolution risk). Top-level side-effect
    registration is likewise observed by the diff, but only takes effect when the package resolves to the same `@breadesp/peripherals` instance as the host.
  - Scanning is **read-only** (a missing root directory = an empty directory rather than an error; broken packages are downgraded to `invalid` entries with all problems listed).
  - Loading MUST be explicitly triggered by the user (§6.6 `per:catalogLoad`), and the target must be an entry with `status='ok'` in the current scan
    (re-scan before loading, preventing import of arbitrary paths via IPC, [BB-224]); entry execution failure or registering no kind reports [BB-223]
    and rolls back the registry (no partial registrations left behind); loading the same directory repeatedly is idempotent. Unload/hot update are out of contract (restarting the app takes effect);
    a failed package can be retried directly once fixed (the entry URL carries an attempt counter to bypass the ESM module cache).
  - After successful loading, the Bridge returns the new kind's factory metadata (`PeripheralMeta`) with the response, and the renderer process mirrors it via
    `registerRemotePeripheral()` as a metadata-only stub — the palette/canvas presents it automatically (§F-EXT-1), and the model's
    `create()` is only instantiated in the Bridge process (misuse reports [BB-207]).
- F-EXT-4 SHOULD provide a peripheral packaging scaffold to lower the bar for starting a new package. P5.3 delivery contract:
  - Command: `pnpm create-peripheral <name> [--display-name <text>] [--description <text>]
    [--dir <parent dir>]`. `name` is lowercase kebab (may carry an `@scope/` prefix); the scope-stripped part serves both as the
    package directory name and the factory kind; `--dir` defaults to the current working directory.
  - Generated artifacts (exactly four files): `breadesp-peripheral.json` (manifest, `sdkVersion` stamped with the host's current
    `PERIPHERAL_SDK_VERSION`, `provides` filled with the generated kind), `index.mjs` (§F-EXT-3 host API injection
    entry + a runnable GPIO level example model), `README.md` (install/load/development guide), `self-check.mjs`
    (zero-dependency smoke test: `node self-check.mjs` self-checks the entry's registration shape and the example model's level behavior).
  - Generator self-validation: the produced manifest MUST pass §F-EXT-3's `validatePeripheralManifest` (zero issues);
    the generated package MUST get `ok` in the directory scan and be loadable and consumable (same path as hand-written packages, no privileges).
  - Error codes: invalid name/options `[BB-230]` (lists all problems; a kind conflicting with an already registered kind belongs to this category too —
    loading would inevitably hit [BB-221], so the scaffold rejects it early); target directory exists and is non-empty `[BB-231]` (the scaffold never
    overwrites existing files; an existing empty directory is allowed to be written). On mid-write failure, clean up the partially created files.

### 3.9 Documentation and Tutorials (F-DOC)
- F-DOC-1 MUST provide an offline documentation site: the in-repo Markdown sources (`README.md`/`docs/README.zh-CN.md`/
  `PRD.md`/`CHANGELOG.md`/`docs/*.md`/`docs/tutorials/*.md` plus their `docs/en/` English mirrors) are built into static
  HTML by `pnpm docs:build`, output to `docs/site/` (gitignored); artifacts carry zero external resources (no CDN
  fonts/scripts/styles, zero JavaScript) and are usable offline. The site is bilingual: Chinese pages occupy the root
  routes and English pages live under the `en/` route prefix; every page carries a topbar language switch pointing at
  the counterpart page (`README.md` ↔ `docs/README.zh-CN.md`).
- F-DOC-2 MUST provide step-by-step tutorials (`docs/tutorials/` and `docs/en/tutorials/`; filename order is tutorial
  order; front-matter carries `title`/`description`; both directories MUST share the same names and order and be
  non-empty): setup and first run, first project (blink LED), debugging workflow, built-in peripheral reference,
  peripheral authoring (SDK + local directory + scaffold), DAP/VS Code integration.
- F-DOC-3 MUST validate in-site link integrity at build time: the target page of a relative link must be in the site manifest and be rewritten to an
  artifact-relative path, and `#anchor` must hit a heading anchor of the target page (GitHub-compatible slug: lowercase, punctuation removed,
  spaces to hyphens, duplicates get a `-N` suffix); all broken links/bad anchors are listed in one pass and fail the build with `[BB-241]`.
  External `http(s):` links are kept as-is and are not validated over the network.
- F-DOC-4 MUST add zero new runtime dependencies (Node built-in modules + existing devDependencies in the repo); the build MUST
  be reproducible: the same input produces byte-identical output (no embedded timestamps, random ids, or host absolute paths).
- F-DOC-5 SHOULD provide local preview: `pnpm docs:serve` rebuilds and statically serves the artifacts (loopback binding,

- F-DOC-6 Documentation site content MUST be consistent with the §6/§7 contracts; code examples MUST be paste-and-run (dev-plan §8.3).
  The documentation site is a pure toolchain: zero IPC changes, zero renderer process changes, zero QEMU device changes.
- Error codes (`packages/docs-site`): `[BB-240]` CLI usage error; `[BB-241]` site content validation failure
  (broken links/bad anchors/missing source files/malformed front-matter/routing conflicts, all listed in one pass); `[BB-242]` read/write failure

## 4. System Architecture (§4)

### 4.1 Layering
```
┌──────────────────────────────────────────────────────────────┐
│ UI 层 (packages/ui, React + Konva)                            │
│  面包板画布 | 器件面板 | 调试面板 | 串口 | 屏幕视图 | 示波器 │
└──────────────────────┬───────────────────────────────────────┘
                       │ IPC (Electron contextBridge / WebSocket)
┌──────────────────────┴───────────────────────────────────────┐
│ Bridge 层 (packages/shell, Node.js / Electron 主进程)          │
│  QemuRunner | GdbBridge | PeripheralManager | NetlistResolver │
│  ProjectManager | IpcHandlers | DBusChannel (socket)         │
└──────────────────────┬───────────────────────────────────────┘
                       │ stdin/stdout + QMP + DBus socket
┌──────────────────────┴───────────────────────────────────────┐
│ Sim Core (packages/sim-core, QEMU-ESP32 + 自定义总线转发设备) │
│  CPU(Xtensa) | Flash/RAM | GPIO/I2C/SPI/UART/I2S/ADC/PWM 模型 │
│  + DBus Forward Device (把总线事务转发到 Bridge socket)       │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 Data Flow (Critical Path)
1. The UI edits the netlist → persists it → sends it to the Bridge over IPC.
2. The Bridge parses the netlist and configures the QEMU launch arguments and peripheral model instances as needed.
3. While the simulation runs:
   - Firmware accesses GPIO/I2C/SPI/I2S → the DBus Forward Device inside QEMU serializes the transaction and sends it to the Bridge socket.
   - The Bridge's PeripheralManager dispatches the transaction to the corresponding peripheral model.
   - The peripheral model updates its internal state (framebuffer/level/PCM) and pushes "render snapshots/events" back to the UI.
4. The UI renders upon receiving a snapshot (Canvas/WebAudio).

### 4.3 Timing Model
- A **logical clock** is used: QEMU advances in virtual time, and the Bridge does not force alignment with wall-clock time.
- Audio peripherals (I2S/buzzer) use a real sample-rate clock (44100Hz, etc.) to avoid audio jitter; other peripherals are event-driven.
- Documentation and UI MUST explicitly state "non-real-time, non-timing-accurate".

## 6. Core Interface Contracts (§6)

### 6.1 Peripheral Pin Definitions
```ts
/** 引脚角色，决定事务如何被外设消费 */
export type PinRole =
  | 'gpio-in'      // 数字输入（外设→MCU），如按键
  | 'gpio-out'     // 数字输出（MCU→外设），如 LED
  | 'pwm-in'       // PWM 输入（MCU→外设），如蜂鸣器
  | 'i2c-sda'      // I2C 数据
  | 'i2c-scl'      // I2C 时钟
  | 'spi-mosi'
  | 'spi-miso'
  | 'spi-sck'
  | 'spi-cs'
  | 'i2s-ws'
  | 'i2s-bck'
  | 'i2s-data-in'   // MCU→外设（喇叭）
  | 'i2s-data-out'  // 外设→MCU（麦克风）
  | 'adc-in'        // 模拟输入（外设→MCU）
  | 'probe'         // 观测探针（P2.5 追加，§F-PER-8 示波器通道：只接收路由事务，不影响信号）
  | 'power'
  | 'gnd';

export interface PinDescriptor {
  id: string;            // 外设内唯一引脚 id，如 'SDA'
  role: PinRole;
  optional?: boolean;   // 是否可选连接
}
```

### 6.2 Peripheral Model Interface (Peripheral SDK Contract)
```ts
import type { BusTransaction, RenderSnapshot } from './types';

export interface PeripheralFactory {
  kind: string;                 // 唯一类型标识，如 'ssd1306'（小写 kebab-case）
  version: string;              // 语义化版本（semver，注册时强制校验）
  displayName: string;
  pins: PinDescriptor[];
  /** 实例省略 props 时的默认参数（如默认 I2C 地址）；NetlistResolver 路由时同以此回退 */
  defaults?: Record<string, unknown>;
  /** 该工厂构建时针对的 SDK 契约版本（P5.1 追加，可选；semver）。缺失 = P5.1 之前的包，按兼容处理 */
  sdkVersion?: string;
  create(ctx: PeripheralContext, props?: Record<string, unknown>): Peripheral;
}

export interface PeripheralContext {
  /** 向 UI 推送渲染快照（如显存帧） */
  emitSnapshot: (snapshot: RenderSnapshot) => void;
  /** 外设 → MCU 上行注入（P3.1 追加：I2S PCM；P3.4 追加：GPIO 电平、I2C 读回复） */
  emitInput?: (injection: PeripheralInjection) => void;
  /** 驱动本实例某个 gpio-in 引脚到 MCU（P3.4 追加；未接线返回 false） */
  drivePin?: (pinId: string, level: 0 | 1) => boolean;
  /** 日志 */
  log: (level: 'info'|'warn'|'error', msg: string) => void;
  /** 逻辑时钟订阅 */
  onTick: (cb: (virtualMs: number) => void) => () => void;
}

export interface Peripheral {
  readonly kind: string;
  readonly instanceId: string;
  /** 收到一条总线事务；viaPin（P2.5 追加）标识事务所经的本实例引脚 */
  onTransaction(tx: BusTransaction, viaPin?: string): void;
  /** GPIO 输入请求（外设主动驱动 MCU 输入，如按键） */
  driveInput?(pinId: string, level: 0|1): void;
  /** 本地采集音频块喂入（P3.2 追加，仅输入类外设实现） */
  acceptCapture?(chunk: CaptureChunk): void;
  /** 旋钮旋转手势（P3.4 追加，正 = 顺时针 detent 步数） */
  rotate?(delta: number): void;
  /** 资源释放 */
  dispose?(): void;
}
```

**Registration and versioning (P5.1, §F-EXT-1/2)**: `@breadesp/peripherals` exports the host SDK contract version
`PERIPHERAL_SDK_VERSION` (currently `1.0.0`; the major is bumped when a breaking change appears in §6.1–6.4). `registerPeripheral()`
enforces factory contract validation at registration time — an illegal shape (kind not lowercase kebab, version not semver, empty displayName,
duplicate pin ids or out-of-range role in pins, missing create, etc.) is rejected with `[BB-220]`; an already registered kind is rejected with `[BB-221]`;
when the major of `sdkVersion` is higher than the major of the host `PERIPHERAL_SDK_VERSION`, it is rejected with `[BB-222]` (the host cannot guarantee
an unknown contract surface). `registerBuiltins()` is idempotent; `validatePeripheralFactory()` is exported for third-party self-checks.
When applying a netlist, the Bridge reports `[BB-206]` for unregistered kinds (including kind/instanceId and registration guidance).

**Directory loading and mirroring (P5.2, §F-EXT-3)**: `PeripheralMeta` (JSON-safe metadata of kind/version/displayName/pins/defaults/
sdkVersion) and `PeripheralHostApi` (`registerPeripheral` + `PERIPHERAL_SDK_VERSION`)
are additive exports; `registerRemotePeripheral(meta)` mirrors kinds already loaded in the Bridge into the current
process's registry as metadata-only stubs (also passing the [BB-220]/[BB-221]/[BB-222] gates; the stub's `create()` reports `[BB-207]`, so models can only be
instantiated in the Bridge); `unregisterPeripheral(kind)` is a host-internal rollback primitive (clearing partial registrations when directory loading fails),
and third-party packages MUST NOT call it.

### 6.5 Netlist (Persisted Netlist)
```ts
export interface Netlist {
  version: 1;
  // P4 起支持多芯片：esp32/esp32s3 走 qemu-system-xtensa（Xtensa），
  // esp32c3/esp32c6 走 qemu-system-riscv32（RISC-V）。
  chip: 'esp32' | 'esp32s3' | 'esp32c3' | 'esp32c6';  // MVP: 'esp32'
  peripherals: PeripheralInstance[];
  wires: Wire[];
}

export interface PeripheralInstance {
  instanceId: string;     // 全局唯一
  kind: string;          // 对应 PeripheralFactory.kind
  props?: Record<string, unknown>;  // 外设特定参数（如 I2C 地址、分辨率）
}

export interface Wire {
  id: string;
  from: { instanceId: string; pin: string };   // 外设引脚
  to:   { instanceId: string; pin: string };   // 另一端（外设或 MCU GPIO）
  // MCU GPIO 用 instanceId='mcu' 表示，pin 为 'GPIO0'..'GPIO39'
}
```

### 6.6 IPC Channels (UI ↔ Bridge)
When generating IPC handlers, AI MUST follow the naming prefixes:
- `sim:*` simulation control (start/pause/step/reset/status)
- `fw:*` firmware loading (load/listSymbols)
- `dbg:*` debugging (setBreakpoint/continue/step/vars/regs; since P4.4 also setConditionalBreakpoint/setWatchpoint/conditionBreakpoint)
- `proj:*` project (new/open/save/saveAs/close; since P4.3 also linkExternal/unlinkExternal/scanExternal/importExternal)
- `bb:*` breadboard (applyNetlist/getNetlist)
- `per:*` peripheral runtime (snapshot events are pushed one-way Bridge→UI; since P5.2 also catalogScan/catalogLoad for local directory scan and load)

All IPC arguments and returns MUST be JSON-serializable (Uint8Array as number[]).

### 6.7 DBus Frame Protocol (QEMU Custom Device → Bridge)
On realize, the `breadesp-dbus` device actively connects to the socket the Bridge listens on (TCP `host`/`port`, or a POSIX `socket` path), and then pushes the intercepted bus transactions as length-prefixed JSON frames:

```
frame   := <uint32 LE payload-length> <payload UTF-8>
payload := {"v":1,"tx":[<tx>,...]};    // v=协议版本，tx=本帧批量事务
tx      := {"kind":"i2c"|"gpio","bus":0,"target":<7bit addr|pin>,
           "dir":"write","ts":<QEMU 虚拟时钟 ns>,"data":[byte,...]}
```

- `ts` is the QEMU virtual clock in nanoseconds; DBusChannel converts it to logical milliseconds when deserializing (the §6.3 contract).
- Frames MUST be flushed in bottom-half batches (multiple transactions triggered by the same instruction go into the same frame).
- The receiving side MUST be fault-tolerant: malformed frames / version mismatches are dropped and the stream continues; an oversized (>64MB) length prefix closes the connection.
- Device-side interception strategy: I2C uses a wildcard slave (ACKing only addresses not occupied by QEMU built-in peripherals); GPIO uses shadow MMIO at both the DPORT(0x3ff44000) and APB(0x60004000) base addresses, passing through raw reads and writes.

Reverse channel (Bridge → device, added as of P3.1, backward compatible): the Bridge may write back length-prefixed frames on the same socket:

```
payload := {"v":1,"in":[<injection>,...]}
i2s-in  := {"kind":"i2s-in","bus":0,"rate":16000,"bits":16,"channels":1,"data":[byte,...]}
gpio-in := {"kind":"gpio-in","pin":4,"level":1}                    (P3.4 追加)
i2c-out := {"kind":"i2c-out","bus":0,"target":68,"data":[byte,...]} (P3.4 追加)
```

- The field order of each kind (i2s-in: bus, rate, bits, channels, data; gpio-in: pin, level; i2c-out: bus, target, data) is part of the protocol (the device side is an ordered scanner, not a full JSON parser). Injection objects with an unknown kind/member are skipped; malformed or oversized (>4MB) reverse frames only disable the reverse path, and the forward transaction stream is unaffected.
- `i2s-in`: the device enqueues the PCM into the injection queue of the corresponding I2S controller (256KB cap per controller; on overflow the oldest data is dropped with a one-time warning), and the RX DMA shadow writes samples into the in-link descriptor buffers at the sample rate decoded by the firmware (owner cleared + length filled back + eof, consistent with the real DMA engine); when the queue runs dry, descriptors stay armed rather than being preempted with silence, avoiding a firmware deadlock in the "re-arm only after receiving data" pattern.
- `gpio-in` (P3.4): the device merges the injected level by pin into the shadow read value of the GPIO_IN/GPIO_IN1 registers (only pins driven by the Bridge are overridden; other bits retain the underlying model value; stock esp32.gpio is a strap-only stub with no qdev input lines, and GPIO edge interrupts are not modeled — input firmware reads them by polling).
- `i2c-out` (P3.4): the device maintains a read-reply mailbox by (bus, target), atomically replacing the pending reply bytes for that key on each frame (matching the sensor read-register "latest value wins" semantics); the I2C sniffer's recv callback supplies them byte by byte, replying 0xFF when the mailbox is empty/exhausted. A reply cannot round-trip within the same synchronous TRANS_START, so firmware should converge by retrying the read.

## 8. MVP Scope (§8, First Milestone)

The MVP MUST complete, and only complete, the following; AI should not over-implement:
1. Load `blink.elf`, start QEMU-ESP32, and see UART0 output.
2. GDB breakpoints/stepping/registers/global variable inspection.
3. Breadboard: LED + push button + SSD1306 OLED, with wiring and project saving.
4. LED turns on and off with GPIO; OLED renders frames correctly; push button injects GPIO input.
5. Simulation control: start/pause/reset/quit.

The MVP explicitly does not do the following (marked TODO, later milestones):
- PWM dimming, I2S speaker/microphone, TFT, oscilloscope, buzzer sound.
- Multiple chip models (ESP32 only).
- DAP adapter (GDB/MI only).
- Online peripheral marketplace.

## 9. Non-Functional Requirements

- **Platform**: Windows / macOS / Linux desktop.
- **Performance**: MVP single-chip simulation, event throughput < 50k transactions/sec is acceptable; OLED frame rate capped at 30fps.
- **Security**: QEMU subprocess sandbox (no network, `-net none`); ELF comes from the user's local machine, and the architecture field is validated before loading.
- **Logging**: the Bridge writes `~/.breadesp/logs/bridge.log`, visible in the UI console.
- **Testability**: peripheral models and netlist validation MUST have unit tests; QEMU integration tests use `blink.elf` as the golden firmware.

## 10. AI Agent Working Conventions (§10, hard constraints)

1. Any code change MUST first confirm the corresponding PRD section and annotate `// PRD: §X.Y` in the file header comment.
2. Do not introduce runtime dependencies not listed in the §5 choice table; a new dependency MUST update §5 and state the rationale.
3. Interface (§6) changes MUST stay backward compatible; breaking changes MUST bump the `version` field and be recorded at the top of the PRD.
4. Generated files MUST land under the §7 paths; do not create undeclared top-level directories.
5. TODO annotation format is uniform: `// TODO(PRD §X.Y): <one sentence>`, for later searchability.
6. Do not place any binary files; QEMU is fetched via `scripts/fetch-qemu.mjs`.
7. UI copy is bilingual Chinese/English (i18n dictionary-driven, technical symbols kept in English); logs and error code messages use English; Chinese is limited to documentation and comments.
8. Any change MUST branch from `main` and be merged via Pull Request; MUST NOT push directly to `main`, MUST NOT use `git commit --no-verify` to skip validation. Commit messages and PR titles MUST comply with `docs/dev-plan.md` §5.2.
